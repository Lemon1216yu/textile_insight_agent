# 数据从哪里来、怎样修改、怎样接入企业系统

本项目没有接入任何企业 ERP，没有下载企业订单，也没有让大模型编造交易明细。默认安装时，Python 把模拟记录写进本机 Docker 的 MySQL；页面和 Agent 查询的是这份库。管理员在网页设置的百炼 Key 只管模型调用，不能用它连接 ERP。

## 1. 三种数据，三个用途

| 内容 | 来源 → 去向 | 默认新部署的数量 |
|---|---|---:|
| 核心业务记录 | [seed.py](../scripts/seed.py) → MySQL。客户 6、产品 6、供应商 3、销售订单 540、生产批次 108、采购 108、库存快照 108、期间费用 54 | 8 表，933 行 |
| 扩展业务记录 | [extended_catalog.py](../textile/extended_catalog.py) 定义表与关联，[seed_extended.py](../scripts/seed_extended.py) 填充。涵盖报价、出货、停机、盘点、质检、应收等 | 44 表 × 12 行 = 528 行 |
| 指标定义 | [metric_catalog.py](../textile/metric_catalog.py) 编写 → 发布到 MySQL 的 metric_registry → 服务读取，Redis 短时缓存 | 32 条，另计 |
| 用来检索的说明 | [retrieval.py](../textile/retrieval.py) 将每张表、每个字段、每条指标各作为一份文档，转为向量写入 Milvus | 52 + 304 + 32 = 388 条 |

因此默认是 **1,461 行业务数据**。不是 1,461 条向量；账号、指标、审计记录也不计入这 1,461 行。查看 MySQL 及 Milvus 的连接方法见[数据库查看指南](DATABASE_GUIDE.md)。

**为什么 7、8 月可能看到利润下滑？** 核心脚本使用固定随机种子 20260914，生成 2026 年 3–8 月样本，每月 90 条销售记录。它刻意把后两个月前两款全棉产品的模拟单位成本乘以 1.25，同时把对应生产批次的疵损比例从 2.5% 设为 7%。这些是为展示分析功能而设计的情景，不是真实企业事件。扩展表使用另一种子 20260915；它们主要验证找表、字段、关联和权限，不能作为完整的采购到付款或订单到收款流水账。

## 2. 想改什么，就改哪一层

| 你的目的 | 怎么做 | 怎么确认生效 |
|---|---|---|
| 在自己的演示库改已有订单或费用 | 用有相应写权限的运维账号在 Navicat 改 MySQL；问数使用的 textile_reader 是只读账号。先确认库名、记录主键，备份原值 | 提交后用只读 SQL 和指标中心核对；相同问题可能命中最长 120 秒结果缓存，已生成的报告不会改写。只改记录无需重建 Milvus |
| 让**下一次全新安装**生成另一批样本 | 改 seed.py 的客户/产品列表、月份、数量、金额规则；扩展表改 seed_extended.py。用**独立 Compose 项目、新卷和空闲端口**验证 | 核心脚本识别 seed_version 中的 textile-v1 后不会覆盖现有交易；扩展脚本只填空表。重启不会重新随机生成全部数据。不用清空原库 |
| 改“营业收入怎么算” | 先确定含税/未税、交付/开票月份、退货处理，再改 metric_catalog.py 的公式、过滤、时间字段和文字说明。在项目根目录执行 `uv run python scripts/publish_metrics.py` | 指标中心核对新版本与试算，再用同期间同区域问数；同步检查总览中的独立 SQL、提示词、示例与回归预期。直接手改 metric_registry 可能被后续发布覆盖 |
| 加表、改字段或名称 | 先做真实建表/迁移，再改 catalog.py 或 extended_catalog.py 的表、字段和关联，更新 permissions.py 的岗位/敏感字段及数据库 GRANT | 执行 `uv run python scripts/build_index.py`，重启 API/worker；用一个有权和一个无权岗位验证。仅改字段含义时向量条数可能不变，不能靠条数判断内容已更新 |
| 换业务期间 | 装载新期间的业务记录，更新 settings.py 的 DATA_PERIOD、前端默认月份/期间文案、指标适用范围与演示问题 | 重建前端并重启服务，确认看板文字、SQL 日期边界和结果一致；只改显示文字不会产生新月份的数据 |

**不用改数据就能验证的一笔账：** 用 Navicat 连接演示库 textile_insight，运行以下只读 SQL。再用全公司经营负责人账号在指标中心选 FIN-005、2026-08。默认样本两个结果都是 **287,590 元**。订单和费用先各自汇总，否则一笔费用可能被每笔订单重复计算。

```sql
SELECT
  (SELECT SUM(net_amount - cost_amount) FROM sales_orders
   WHERE order_status = '已完成'
     AND delivery_date >= '2026-08-01' AND delivery_date < '2026-09-01')
  -
  (SELECT SUM(amount) FROM finance_expenses
   WHERE expense_date >= '2026-08-01' AND expense_date < '2026-09-01')
  AS operating_profit_yuan;
```

## 3. 真正对接企业：先接通一个指标

**目前没有通用 ERP 连接器、网页导入向导或自动同步任务。** 建议第一期只做“一个月、一个区域、确认销售收入”，验收后再接成本与费用。以下是实施方案，不是仓库已经接通的接口。

企业 ERP/MES/WMS/财务系统 → 经授权的只读视图、正式 API 或定期文件 → 暂存区 → 清洗/对账 → 专用 MySQL 分析库 → ChatBI 只读查询。Milvus 接表结构和指标说明，不需要导入全部真实订单。

例如接 SAL-001，以下源字段仅为**示例**，必须由企业 IT 用实际数据字典替换：

| 企业侧要找什么 | 分析侧要得到什么 | 上线前要问清 |
|---|---|---|
| 出货单号、行号、拆批记录 | 唯一且稳定的交付明细标识，保留到源单的映射 | 项目样本每笔订单只有一条销售记录。真实订单分三次出货，要按交付行建事实，不能把订单总额抄三次。订单数也不能直接数交付行 |
| 实际过账/出货日、状态码 | delivery_date、标准业务状态 | 若企业按开票日确认收入，则必须另定义开票口径，不能把出货日改名冒充开票日 |
| 未税金额、币种、退货红字 | 可按期间汇总的人民币未税净额 | 税额如何剔除？用哪个汇率、哪天折算？退货扣在哪个月？没有确认前不合并不同币种 |
| 客户、物料、销售组织 | customer_id、product_id、region | 用稳定编码做关联；区域按约定的业务归属映射，不用客户名称猜区域 |
| 实际结转成本、期间费用凭证 | 后续接 FIN-005 的成本及独立费用表 | 没有实际成本就先只上线收入；不要用标准成本补成“实际毛利” |

**实施和验收顺序：**

1. **取样。** IT 提供系统名称/版本、授权的接口或脱敏导出、字段字典；业务提供同月同区域的权威报表。先拿包含正常、取消、部分交付、退货的样例即可。不要在聊天或仓库中发生产密码。
2. **建立隔离。** 使用独立分析库、服务账号和独立索引；演示库保留。对接层可写暂存区，Agent 只读获准业务表。账户/审计写权限与业务查询分开。当前初始化脚本含 root、固定授权库名及模拟填数逻辑，**不要把 .env 指向生产库后直接运行 start.ps1 或 seed.py**。企业部署需要另设迁移/启动流程，禁用扩展表自动填数。
3. **同步。** 首次按期间全量；之后以源记录唯一键去重，以更新时间增量同步，成功提交后才推进水位。处理晚到、作废、红冲与重跑。记录批次、源/目标行数、金额和异常行；保留上一批可回退数据。同步器需按真实系统开发。
4. **对账。** 固定同一期间、区域、币种、时区和截止时间，对比“企业权威报表 → 分析库 SQL → 指标中心 → 智能问数”。先对总额，再按客户、日期下钻到单据；差异由业务解释并签认。对账通过前保持试运行，不用模拟基准 287,590 元验收真实企业。
5. **验证边界。** 销售经理不能看到其他区域或成本，财务能查授权范围。当前模型调用会发送问题、授权范围内的 Schema/指标说明；多步分析还可能发送执行 SQL 和返回的结果行。先由企业确定哪些数据允许发给模型服务；不允许时需做脱敏、聚合或更换获准的内部推理服务，不能只换一个 Key。

交付验收物是：**源到目标字段映射、已确认的指标口径、可重跑的同步任务、同期间对账结果、岗位权限测试记录**。没有真实系统接口和业务确认前，只能称为“可对接的 MVP”。
